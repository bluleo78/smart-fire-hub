## 내가 정한 것
- 1: `proactiveExecutor` 코어 = 최대 = 5(큐 50 유지). 큐에서 기다리는 상태를 화면에 보이는 것은 범위 밖 — 잡마다 슬롯이 하나라 큐에 쌓이는 것은 서로 다른 잡 5개가 동시에 돌 때뿐이다.
- 2·3: 슬롯 획득 → 비동기 제출 → 제출 실패 시 슬롯 해제를 **한 서비스 메서드**로 모아 수동(컨트롤러)·예약(스케줄러)·이상 감지 세 경로가 같이 쓴다. 예약 실행도 슬롯을 잡고, 이미 돌고 있으면 그 회차는 건너뛰고 log.info 한 줄(실행 행 없음). 모든 경로가 슬롯을 잡은 뒤 제출하므로 러너 `finally` 의 해제는 늘 자기 슬롯이다.
- 4: `PUT /settings` 에 `ai.model` 이 실리면 지금 테넌트 채팅 자격증명 유형으로 **채팅 경로와 같은 검사**(`AiChatRequestBuilder` 89행 부근의 `credential.modelProblem`)를 해 문구 그대로 400. 자격증명이 아직 없으면 검사하지 않는다(모델을 먼저 고르는 순서를 막지 않게).
  - 구현 중 발견: 웹 `SettingsPage.performSave` 가 모델 PUT 을 자격증명 PUT 보다 **먼저** 보내, 유형과 모델을 한 번에 바꾸는 저장(sdk→opencode+`openai/gpt-4o`, opencode→sdk+`claude-sonnet-4`, opencode 공급자 바꾸기)이 저장된 옛 유형으로 검사돼 400. 자격증명 PUT 도 opencode 일 때 저장된 모델과 공급자 일치·목록을 검사해(AiCredentialController 72-79), 순서만 바꾸면 opencode 공급자 바꾸기가 막힌다.
  - **리뷰 뒤 다시 정함(최종)**: 요청 두 개의 순서로 푸는 방식은 어느 순서든 구멍이 남는다(묵은 슬래시 모델이 있을 때 sdk→opencode 교착, opencode 검사 건너뜀, 자격증명만 Claude 계열로 바꾸는 길이 열림, 되돌리기 거짓 경보). → 채팅 자격증명 PUT 이 선택적 `model` 을 받아 **자격증명과 모델을 한 트랜잭션으로 검사·저장**한다(분류 자격증명 saveClassify 와 같은 모양). 검사는 바뀐 뒤의 짝(새 유형 × 새 모델, 모델이 없으면 저장된 모델)으로: Claude 계열은 modelProblem, opencode 는 기존 공급자 일치·목록 확인을 그 모델로. 웹은 유형·자격증명과 모델을 함께 바꾸면 이 한 요청으로 보낸다(순서·되돌리기 없음). `PUT /settings` 의 `ai.model` 단독 저장은 저장된 자격증명 기준 검사 그대로.
  - (이전 안) 서버 검사는 저장된 자격증명이 Claude 계열일 때만(opencode 저장이면 검사 없음 — 자격증명 PUT 이 지킴). 웹은 지금 순서(모델 먼저)를 두고 **Claude 계열 → opencode 유형 바꾸기**일 때만 자격증명 먼저·모델 뒤(모델 실패 시 자격증명 되돌리기). sdk→opencode·opencode→sdk·opencode 공급자 바꾸기·sdk 단독 슬래시 모델(400) 네 경우를 E2E·단위 시험으로 확인.
- 5: `app.proactive.agent-timeout` 이 10초 미만(0·음수 포함)이면 기동 실패(`IllegalStateException` — 설정 키 이름과 받은 값을 문구에).
- 6: 캔버스 위에 떠 있는 「자동 정렬」·「스텝 추가」 outline 버튼에 `bg-background` 를 준다(공용 outline 은 그대로 투명).
- 7: 표 감싸개는 카드 안(`data-slot="card"` 조상)이면 칠하지 않는다(Tailwind v4 `in-data-[slot=card]:bg-transparent` 등 — 동작 확인). 주석도 다크 사실에 맞게.
- 8: `row-divider` 선택자 특이도를 한 클래스(0,1,0)로(`:where(:not(:last-child))`). 같은 특이도에서 `border-b-0` 같은 한 클래스 덮어쓰기가 실제로 이기는지(유틸 순서) 확인하고, 지지 않으면 이기게 하는 방법을 고른다.
