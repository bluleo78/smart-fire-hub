# WD-770 운영자 콘솔 멤버 추가 — 「새 계정」 탭의 기존 이메일 안내 (작은 변경)

## 왜
테넌트 상세 › 멤버 추가 › 「새 계정」 탭에 이미 계정이 있는 이메일을 넣으면 서버(`TenantMemberAdder`)는 username(=정규화 이메일)으로
기존 계정을 찾아 멤버십만 붙이고 `created=false` 를 준다. 입력한 이름·임시 비밀번호는 쓰지 않는다. 지금 화면은 이때 「<입력한 이름>님을
멤버로 추가했습니다」 토스트만 띄우고 닫아, 운영자가 복사해 둔 임시 비밀번호가 적용되지 않았다는 것을 모른다(WD-750 리뷰 비차단 결함).

## 목표
1. **제출 전 안내**(WD-751 웹 방식과 맞춤): 「새 계정」 탭 이메일 칸에서 포커스가 빠지면(형식이 맞을 때) 계정 목록
   (`GET /api/platform/accounts?q=<정규화 이메일>&page=0&size=20`, 비활성 포함·username 을 준다)으로 그 이메일의 계정이 있는지 본다.
   결과 중 `username` 이 정규화(trim·소문자) 이메일과 같은(대소문자 무시 — 서버 `findByUsernameIgnoreCase` 와 같은 뜻) 계정이 있으면:
   - 이 테넌트의 멤버가 아닌 활성 계정: 칸 아래에 「이미 가입된 계정입니다 — <이름>(<아이디>). 새 계정을 만들지 않고 이 계정을 멤버로
     추가합니다.」 안내와 「기존 계정으로 추가」 버튼을 보인다. 버튼은 「기존 계정」 탭으로 바꾸고 그 계정을 골라 둔다(ADMIN 체크는 그대로).
   - 이미 이 테넌트의 멤버(WD-773): 「이미 이 테넌트의 멤버입니다 — <이름>(<아이디>).」(정지 멤버면 「…(정지됨) — … 멤버 상태를
     확인하세요.」)만 보이고 버튼은 두지 않는다 — 제출해도 409 `MEMBER_ALREADY_EXISTS`·`MEMBER_SUSPENDED` 다.
   - 비활성 계정·조회 실패·조회 중·멤버 목록을 모를 때: 안내하지 않는다.
2. **제출 뒤 안전망**: 「새 계정」 탭 요청에 `created=false` 가 오면(사전 확인이 놓친 경우 — 검색 실패, 확인 전 제출, 멤버 목록을 몰라 안내하지 않은 경우)
   경고 토스트 「이미 있는 계정(<정규화 이메일>)이라 기존 계정으로 추가했습니다 — 입력한 이름·임시 비밀번호는 쓰지 않았습니다」를 보이고
   닫는다. 이름은 서버가 주지 않으므로 입력한 이름 대신 실제 로그인 아이디(이메일)를 보인다.
3. **같은 리뷰의 선택 항목**: 로그인한 운영자가 `/signup` 을 직접 열면 첫 가입 폼 대신 `/tenants` 로 보낸다. (「가입은 됐는데 로그인
   실패」 구분은 WD-749 에서 이미 `SignupSessionError`·「계정은 만들어졌습니다. 로그인해 주세요.」로 들어가 있어 할 것이 없다.)

## 하지 않는 것
- API 변경 없음(응답에 계정 이름 추가, 존재 확인 전용 API 등). 검색 API 는 `platform:member:read` 권한으로 이미 화면이 쓰는 것이다.
  **단, WD-773 이 `GET /api/platform/accounts` 의 검색 정렬을 바꿨다** — username 정확일치(대소문자 무시)를 맨 앞에, 그다음 기존
  순서. 요청·응답 모양은 그대로다(아래 「WD-773 보완」).
- 안내가 떠도 「새 계정」 탭 제출을 막지 않는다 — 막지 않아도 안전망이 결과를 분명히 알린다.
- ~~이미 멤버인지 사전 판정하지 않는다~~ → WD-773 에서 사전 판정한다(아래). 제출 뒤 서버 409 안내도 그대로 있다.

## 접근
- (가) 제출 전 확인 + 안전망 — **채택**. 이슈가 권한 웹(WD-751) 방식과 맞추고, 확인이 놓치는 경우도 안전망이 덮는다.
- (나) 안전망만 — 가장 작지만 운영자가 비밀번호를 복사·전달하기 전에 알 수 없다.
- (다) 서버 응답에 계정 이름 추가 — API·두 벌 저장소 변경이 필요한데 얻는 것은 토스트의 이름뿐이다.

## 내가 정한 것
- 사전 확인 일치 기준은 계정 목록 결과의 `username` 정확 일치(대소문자 무시). 서버가 새 계정 요청에서 기존 계정을 찾는 규칙과 같다 —
  (초안의 사용자 검색 `GET /api/platform/users` + `email` 일치는 구현에서 이렇게 바뀌었고 WD-773 에서 문서를 맞췄다.)
- 검색 실패·진행 중에는 안내를 띄우지 않는다(조용히 넘어가고 안전망에 맡긴다).
- 이메일을 다시 고치면 안내는 새 확인 결과로 바뀐다(이전 결과를 남기지 않는다).

## WD-773 보완 (WD-770 리뷰 비차단 결함)
- **대소문자**: username 비교를 `a.username.toLowerCase() === checkedEmail` 로 — 대문자가 섞여 저장된 username 도 기존 계정이다.
- **캐시 무효화**: 확인 쿼리 키를 `['platform-accounts', 'email-check', <정규화 이메일>]`(머리는 `PLATFORM_ACCOUNTS_KEY` 상수)로 옮겨 계정 생성(`CreateAccountDialog`)·
  비활성화·재활성화(`AccountListPage`)·멤버 추가(`TenantDetailPage`)의 `['platform-accounts']` 접두 무효화에 함께 걸리게 했다. 응답 모양은
  계정 화면 키(`['platform-accounts', params]`)와 같은 `PageResponse` 이고 두 번째 요소가 문자열이라 겹치지 않는다. 무효화 뒤 다시 읽는
  동안에는 낡은 결과로 안내하지 않는다.
- **20건 너머**: 서버 계정 목록 검색 정렬을 「username 정확일치(대소문자 무시) → 이메일 정확일치 → 이메일 → 이름 → id」로 바꿨다
  (jOOQ·MyBatis 두 구현). 부분일치가 20건을 넘어도 정확일치 계정이 첫 쪽에 온다. username 유일 제약은 대소문자를 가려 대소문자만 다른
  계정이 여럿일 수 있는데, 서버 `findByUsernameIgnoreCase` 는 그중 최소 id 를 붙이므로 화면도 최소 id 를 고른다(정렬은 그 안의 순서를 정하지 않는다).
  검색어 없는 기본 정렬(생성 최신순)과 Owner 검색 정렬은 그대로다.
- **이미 멤버**: 테넌트 상세 멤버 표와 같은 캐시(`GET /api/platform/tenants/{id}/members`)로 계정 id 를 대조한다. 이 API 는 페이지 없이
  상태 무관(ACTIVE·SUSPENDED) 전체 멤버를 주므로 「멤버 아님」 판정이 일부 목록에 기대지 않는다. 목록을 아직 못 읽었거나 실패했으면 멤버 여부를
  모르므로 「기존 계정으로 추가」를 권하지 않는다. 새 API 는 만들지 않았다. 「새 계정」 탭이 마운트될 때 멤버 목록을 스스로 다시 읽고(`refetchOnMount: 'always'`),
  다시 읽는 중이거나 실패하면 역시 「모름」으로 둔다(화면을 연 뒤 바뀐 멤버십을 낡은 캐시로 판정하지 않게). 호출자가 목록을 넘기지 않는다.
- **비활성 계정**: 서버가 이미 멤버인지보다 비활성(409 `ACCOUNT_INACTIVE`)을 먼저 거부하므로, 비활성 계정이면 멤버여도 아무 안내도 하지 않는다.
  「(정지됨)」 꼬리표는 멤버십 상태가 `SUSPENDED` 일 때만, 그 밖의 비활성 상태는 꼬리표 없는 문구다.
- **멤버 추가 뒤 무효화**: `['platform-accounts']` 를 `refetchType: 'none'` 으로 낡음 표시만 한다 — 곧 사라질 사전 확인 쿼리의 낭비 요청을 막고,
  다시 열면 낡은 쿼리라 새로 조회한다.
