# WD-771 web 멤버 추가 기존 계정 확인 후속 — 설계

## 왜
WD-751 로 web 멤버 추가 대화상자는 이메일로 계정을 먼저 확인한다(`POST /api/v1/users/member-lookup`). 리뷰에서 다음 다섯 가지가 비차단으로 남았다.
- 비활성 계정을 「기존 계정 — 기존 비밀번호로 로그인」이라고 잘못 안내한다.
- 409 를 받은 뒤에도 판정이 EXISTING 으로 남는다.
- 비멤버 계정의 내부 userId 를 응답에 싣는다.
- 확인 응답을 기다리는 동안 대화상자를 닫을 수 없다.
- 다른 멤버 추가 E2E 들에 lookup 모킹이 없다.

## 고칠 것
1. **비활성 계정(이슈 1)**
   - api `MemberLookupResponse.Status` 에 `INACTIVE` 를 더한다. 계정이 있고 `is_active=false` 이며 이 워크스페이스 비멤버일 때 쓴다. 멤버십이 있으면 지금처럼 MEMBER·SUSPENDED 다.
   - api `UserService.addMember`: 기존 계정이 비멤버이고 비활성이면 409 `ACCOUNT_INACTIVE` 로 거부한다. 문구는 운영자 콘솔(`PlatformTenantMemberAddTransaction.rejectIfInactive`)과 같게 쓴다.
     - 판정 순서: 역할 검증 → 역할 범위 → 이미 멤버(409) → **비활성(409)** → 새 계정 필드(400) → 생성.
   - web: 판정이 `INACTIVE` 면 이름·임시 비밀번호 칸을 숨기고 아래 안내를 보이며, 제출을 잠근다(이미 멤버와 같은 `disabled`).
     - 안내: 「비활성화된 계정입니다 — {이름}. 계정이 다시 활성화되기 전에는 멤버로 추가할 수 없습니다. 플랫폼 운영자에게 활성화를 요청하세요.」
   - 제출 뒤 409 `ACCOUNT_INACTIVE`(판정과 제출 사이에 비활성화된 경우)를 받으면 판정을 `INACTIVE` 로 바꿔 같은 안내를 보이고, 버튼이 잠기며 포커스가 사라지지 않게 이메일 칸으로 옮긴다.
     - 응답을 기다리는 사이 이메일을 고쳤으면 판정은 두지 않고, 버튼 위 오류로 「제출한 이메일({이메일})은 비활성화된 계정이라 추가하지 못했습니다」를 보인다.
   - api `addMember` 는 계정·멤버십을 존재 확인과 같은 `findMemberCandidate` 로 한 번에 얻는다. 새 계정 경로에서 조회와 추가 사이에 계정이 생긴 경합에도 `TenantMemberAdder.add` 에 `rejectIfInactive` 를 넘겨 비활성 계정을 거부한다.
2. **409 뒤 판정 갱신(이슈 2)**: 409 의 `code` 별로 판정을 바꾼다.
   - `MEMBER_ALREADY_EXISTS` → 판정 `MEMBER`. 이미 멤버 안내(배너)가 보이고 제출이 잠긴다. 같은 문구의 칸 오류는 두지 않고(칸 오류 대신 배너), 포커스는 이메일 칸으로 옮긴다.
   - `MEMBER_SUSPENDED` → 판정 `SUSPENDED`(userId 는 응답 `errors.userId`). 지금의 칸 오류·상세 링크는 그대로 두고 제출이 잠긴다. 칸 오류가 떠 있는 동안 정지 멤버 배너는 그리지 않는다(같은 링크가 두 번 나오지 않게).
   - 그 밖의 알 수 없는 409 → 판정을 바꾸지 않고 이전처럼 서버 문구를 이메일 칸 오류로 보인다.
   - 응답을 기다리는 사이 이메일을 고쳤으면 판정을 두지 않는다(이미 멤버면 버튼 위 오류로 제출한 이메일을 알린다).
3. **비멤버 userId(이슈 3)**: `EXISTING`·`INACTIVE` 응답의 `userId` 는 null 이다. `MEMBER`·`SUSPENDED` 만 userId 를 싣는다(상세 링크용).
4. **확인 대기 중 닫기(이슈 4)**
   - 제출 직전 확인(`checkingOnSubmit`)만 도는 동안에는 취소·Esc·바깥 클릭으로 닫을 수 있다. 실제 제출(`isSubmitting`) 중의 잠금은 그대로 둔다.
   - 닫힌 뒤 늦게 온 확인 응답은 무시한다. 판정·제출에 쓰지 않는다.
   - 다시 열면 새 상태로 시작한다.
5. **E2E lookup 모킹(이슈 5)**
   - 공용 픽스처(`e2e/fixtures/admin.fixture.ts` 등 멤버 추가 spec 들이 쓰는 곳)에 `POST /api/v1/users/member-lookup` → `{status:'NEW', userId:null, name:null}` 기본 모킹을 더한다.
   - 대상 spec 은 `admin-submit-focus`·`member-lifecycle`·`audit-logs-security`·`admin-permission-access` 다. 각 spec 이 따로 모킹하면 그쪽이 이긴다.

## 시험
- **api:** 아래를 단위·통합으로 시험한다.
  - `lookupMember` 판정: 비활성 비멤버 → INACTIVE, userId null. 활성 비멤버 → EXISTING, userId null. 멤버·정지는 userId 를 싣는다.
  - `addMember` 거부: 비활성 비멤버 → 409 ACCOUNT_INACTIVE, 아무것도 쓰지 않는다. 비활성인데 이미 멤버면 지금의 409 그대로.
- **web E2E**(`member-add.spec.ts`):
  - INACTIVE 안내·제출 잠금
  - 제출 409 ACCOUNT_INACTIVE → 안내
  - 「이미 멤버」 409 뒤 이미 멤버 안내·버튼 잠김(다시 눌러도 요청 없음), 칸 오류 없음, 포커스 이메일 칸
  - 409 `ACCOUNT_INACTIVE`(Enter 제출) 뒤 포커스 이메일 칸, 응답 사이 이메일을 고쳤으면 제출한 이메일 오류
  - 409 `MEMBER_SUSPENDED` 뒤 정지 판정·잠금, 코드를 모르는 409 는 칸 오류·판정 불변
  - 409 로 MEMBER 가 된 뒤 이메일을 고치면 배너가 사라지고 버튼이 켜지며 blur 때 다시 확인
  - 확인 응답을 붙잡은 상태에서 취소·Esc 로 닫히고, 늦은 응답 뒤에도 다시 열면 깨끗함
- **api:** 새 계정 경로 경합(첫 조회는 계정 없음, add 의 조회는 비활성 계정) → 409 ACCOUNT_INACTIVE, 멤버십 없음.

## 하지 않는 것
- 비활성 멤버(멤버십 있음)의 처리 변경, 운영자 콘솔 경로 변경, 확인 요청 타임아웃 도입(닫기로 충분).

## 내가 정한 것
- 비활성 계정은 안내와 거부를 둘 다 한다.
  - 운영자 콘솔 경로가 이미 거부한다.
  - 워크스페이스 관리자는 플랫폼 계정을 활성화할 수 없다.
  - 그래서 붙여도 로그인하지 못하는 멤버만 생긴다.
  - 이렇게 하면 WD-750 의 「웹 동작 불변」 결정을 이 경우에 한해 바꾸는 셈이다. 이슈가 「안내하거나 거부」를 허용했다.
- 409 뒤에는 다시 확인하지 않고 MEMBER 로 바로 바꾼다. 서버가 이미 「멤버다」라고 답했으므로 요청을 한 번 아낀다.
- 두 경로의 판정 순서가 다르다: 웹은 이미 멤버 → 비활성, 운영자 콘솔은 비활성 → 이미 멤버. 콘솔 동작은 바꾸지 않는다(「하지 않는 것」). 웹의 새 계정 경로 경합(조회와 추가 사이에 계정이 생김)은 `TenantMemberAdder.add` 의 순서를 따라 비활성이 먼저다 — 새로 생긴 계정이 비활성이면서 이미 이 워크스페이스 멤버인 경우는 드물어 받아들인다.
- INACTIVE 판정은 멤버 추가 권한이 있는 관리자에게 다른 워크스페이스 계정의 비활성 여부를 알려 준다. 기존 EXISTING 도 계정 존재·이름을 알려 주고, 이 정보 없이는 추가가 409 로만 막혀 안내할 수 없으므로 받아들인다(코드 변경 없음).
