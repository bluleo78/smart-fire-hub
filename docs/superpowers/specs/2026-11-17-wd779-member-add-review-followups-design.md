# WD-779 멤버 추가 리뷰 후속(WD-771 PR #1038) — 설계

## 왜
WD-771 리뷰에서 머지를 막지 않은 결함 6건이 남았다(이슈 본문 1~6). 모두 관리 › 멤버 추가 흐름이다.

## 고칠 것

### api
1. **계정 생성 경합 코드 분리(이슈 1의 서버 쪽):** `TenantMemberAdder.attach` 는 어떤 `DuplicateKeyException` 이든 409 `MEMBER_ALREADY_EXISTS` 로 바꾼다.
   - 새 계정을 만드는 중(계정 확보 단계)에 걸린 유일 제약이면 409 `ACCOUNT_ALREADY_EXISTS` 로 낸다. 문구: `같은 이메일의 계정이 방금 만들어졌습니다. 다시 확인한 뒤 추가하세요`.
   - 멤버십·역할 단계에서 걸리면 지금처럼 `MEMBER_ALREADY_EXISTS` 다.
2. **워크스페이스 경로의 비활성 문구(이슈 5):** 코드는 둘 다 `ACCOUNT_INACTIVE` 로 같고, 문구만 경로별로 다르다.
   - 운영자 콘솔: `비활성화된 계정은 멤버로 추가할 수 없습니다. 먼저 계정을 활성화하세요`(지금 그대로).
   - 웹(워크스페이스 관리자): `비활성화된 계정은 멤버로 추가할 수 없습니다. 플랫폼 운영자에게 계정 활성화를 요청하세요`.
3. **판정 순서 하나·조회 하나(이슈 6):**
   - `TenantMemberAdder.addExisting` 이 호출자 검사(`Consumer<UserResponse>`)를 받아 `rejectIfAlreadyMember` **뒤에** 부른다. `add` 의 기존 계정 경로도 같은 순서로 넘긴다.
   - 그래서 모든 경로(웹 일반·웹 경합·콘솔 이메일·콘솔 id)가 **이미 멤버 → 비활성** 순서가 된다.
   - `UserService.addMember` 는 멤버십을 따로 조회하지 않고, 계정만 찾아 `addExisting(…, 웹 비활성 검사)` 를 부른다.
   - 운영자 콘솔에서 「비활성이면서 이미 멤버」인 계정은 `ACCOUNT_INACTIVE` 대신 `MEMBER_ALREADY_EXISTS`/`MEMBER_SUSPENDED` 를 받는다(콘솔 동작이 이 경우만 바뀜).

### web — `AddMemberDialog.tsx`
4. **경합 409 뒤 다시 확인(이슈 1):** 제출이 409 `ACCOUNT_ALREADY_EXISTS` 를 받으면 그 이메일로 lookup 을 한 번 다시 해 판정을 바꾸고, 버튼 위 오류로 `같은 이메일의 계정이 방금 만들어져 추가하지 못했습니다 — 확인 결과를 보고 다시 추가하세요` 를 보인다. 응답 사이 이메일을 고쳤으면 다시 확인하지 않고 버튼 위 오류 `제출한 이메일({이메일})은 계정이 방금 만들어져 추가하지 못했습니다 — 다시 확인한 뒤 추가하세요` 를 보인다(다른 409 와 같은 규칙 — 다시 확인하지 않았으므로 「확인 결과를 보고」 대신 「다시 확인한 뒤」).
5. **정지 409 와 이메일 수정(이슈 2):** `MEMBER_SUSPENDED` 도 `replaceVerdict` 결과를 본다. 이메일을 고쳤으면 칸 오류·링크를 달지 않고 버튼 위 오류 `제출한 이메일({이메일})은 정지된 멤버라 추가하지 못했습니다` 를 보인다.
6. **제출 직후 닫기 틈(이슈 3):** 실제 제출이 시작되는 순간 ref 를 세우고(끝나면 내림), `handleOpenChange` 의 닫기 잠금이 렌더 시점 `isSubmitting` 과 이 ref 를 함께 본다.
7. **주석 자리(이슈 4):** `VERDICT_CONFLICTS` 를 `copyText` 의 JSDoc 위로 옮겨 `copyText` 가 제 설명을 되찾게 한다.

## 하지 않는 것
- lookup 호출 제한(이슈 「참고」) — 별도 판단.

## 내가 정한 것
- 경합 판정은 서버가 코드를 나눈다(DB 제약 이름을 파싱하지 않고, 계정 확보 단계에서 났는지로 가른다). 웹이 모든 `MEMBER_ALREADY_EXISTS` 뒤에 다시 확인하면 정상 경로에도 요청이 하나 더 들고, 콘솔·AI 도구 같은 다른 클라이언트는 여전히 틀린 코드를 받는다.
- 판정 순서는 「이미 멤버 → 비활성」으로 통일한다. 이미 멤버라는 사실이 더 구체적인 답이고(멤버면 활성 여부와 상관없이 추가할 것이 없다), 웹이 이미 이 순서다. WD-771 이 「콘솔 동작 불변」으로 남겨 둔 차이를 이 이슈가 풀라고 했다.

## 시험
- api(`MemberAddServiceTest`, 콘솔 쪽 시험):
  - 경로별 코드·문구: 웹 비활성 비멤버 → `ACCOUNT_INACTIVE` + 웹 문구, 콘솔 → 콘솔 문구.
  - 비활성 + 이미 멤버 → 웹·콘솔 모두 `MEMBER_ALREADY_EXISTS`(정지면 `MEMBER_SUSPENDED`).
  - 새 계정 경로에서 계정 생성이 유일 제약에 걸림 → 409 `ACCOUNT_ALREADY_EXISTS`, 아무것도 남지 않음.
- web E2E(`member-add.spec.ts`):
  - 409 `ACCOUNT_ALREADY_EXISTS` → lookup 재요청, 판정이 그 결과(EXISTING)로 바뀌고 버튼 위 오류.
  - 정지 409 를 기다리는 사이 이메일 수정 → 칸 오류·링크 없음, 버튼 위 오류.
  - 제출 시작 직후 Esc → 닫히지 않고 결과 화면이 뜬다.
